# التعامل الآمن مع بيانات خدمة حكومية

هذه المذكرة عملية للمسابقة وليست استشارة قانونية. الهدف أن يعمل المساعد كمصدر
معلومات عن الخدمة، لا كنظام معاملات أو نظام لاتخاذ قرار عن الأشخاص.

## ما الذي قد يصلنا؟

وجود عبارة «خدمة حكومية» لا يعني تلقائياً أن الملفات سرية. الاحتمال الأكبر أن تكون
أدلة خدمة عامة: الشروط، الوثائق المطلوبة، الرسوم، المدد، الفئات المستفيدة، خطوات
التقديم، الأسئلة الشائعة، النماذج الفارغة ومعلومات الاتصال الرسمية. هذه مناسبة لـRAG.

لكن قد تظهر بالخطأ نماذج معبأة أو سجلات حالة فردية. هنا نوقف الفهرسة ونراجع الملف.

| التصنيف | أمثلة | قرار النظام |
|---|---|---|
| عام | دليل خدمة، رسوم، شروط، ساعات عمل | يفهرس محلياً |
| يحتاج مراجعة | بريد أو هاتف قد يكون جهة رسمية | يفهرس مع تنبيه للمراجعة |
| مقيّد | رقم وطني، جواز، IBAN، بطاقة دفع، كلمة مرور أو مفتاح | يعزل ولا يفهرس افتراضياً |
| حساس جداً | صحة، بصمة حيوية، وضع مالي، سجل جنائي أو سياسي مرتبط بشخص | لا يستخدم في نسخة العرض قبل موافقة واضحة وضوابط رسمية |

القانون الأردني يعرّف البيانات الشخصية بأنها ما يعرّف شخصاً طبيعياً مباشرة أو بصورة
غير مباشرة، ويعد الوضع المالي والصحي والجيني والبيومتري والسجل الجنائي وغيرها بيانات
حساسة. لذلك لا نكتفي بإخفاء الاسم؛ جمع عدة تفاصيل قد يعيد تعريف الشخص.

## الخطوط الحمراء في المساعد

1. لا إرسال للوثائق أو الأسئلة إلى API سحابي. Ollama، الـembedding، Chroma والواجهة
   تعمل كلها على الجهاز المحلي.
2. لا Web Search أو Analytics أو Telemetry أثناء العمل على بيانات المسابقة.
3. لا نطلب من المستخدم رقماً وطنياً أو جوازاً أو هاتفاً أو بريداً أو بيانات مالية.
4. لا ننفذ معاملة ولا نتحقق من أهلية شخص بعينه؛ نشرح القواعد العامة من الوثائق.
5. لا نعرض إجابة بلا مصدر وصفحة واقتباس حرفي قابل للتحقق.
6. لا نخزن نص السؤال أو الجواب في السجلات. السجل التشغيلي يحتوي معرف طلب وأزمنة
   ومعرفات chunks فقط.
7. لا نفهرس ملفاً مقيّداً تلقائياً. الاستثناء يتطلب مراجعة يدوية وفهماً واضحاً لطبيعة
   بيانات المسابقة.
8. نحذف ملفات المسابقة والفهرس والسجلات من الجهاز بعد انتهاء الحاجة إليها وفق تعليمات
   المنظمين، ولا نرفعها إلى GitHub.

## ما يفعله الكود الآن

- يفحص الملفات قبل التنظيف حتى لا تختفي محارف أو تعليمات خبيثة.
- يسجل بصمة SHA-256 ومصدر كل ملف.
- يعزل محاولات prompt injection عالية الخطورة.
- يصنف مؤشرات الخصوصية من دون نسخ القيمة الحساسة إلى التقرير.
- يمنع السؤال المحتوي على مؤشرات هوية أو اتصال أو بيانات مالية قبل الاسترجاع وقبل
  استدعاء النموذج، ويطلب إعادة صياغته بصورة عامة.
- يجيب من الدليل فقط، ويفشل بصورة مغلقة عند غياب اقتباس صحيح.

## ما لا يستطيع الفاحص الآلي ضمانه

لا يمكن لتعبيرات نمطية معرفة كل اسم أو عنوان أو حالة صحية، ولا تستطيع وحدها تحديد ما
إذا كان رقم الهاتف عاماً لمؤسسة أو خاصاً بفرد. لذلك تبقى معاينة الملفات والتقرير خطوة
إلزامية. عند الشك، نعامل الملف كمقيّد ولا ندخله الفهرس.

## سيناريو العرض للحكام

1. نوضح أن الشبكة غير مطلوبة وأن كل المكونات محلية.
2. نعرض تقرير الجرد: الملفات العامة، الملفات التي تحتاج مراجعة، والملفات المعزولة.
3. نسأل بالعربية ونظهر الجواب والصفحة والاقتباس.
4. نسأل السؤال نفسه بالإنجليزية؛ يظهر جواب إنجليزي مع بقاء الاقتباس العربي كما هو.
5. نكتب سؤالاً يحوي رقماً وطنياً تجريبياً؛ توقفه بوابة الخصوصية قبل النموذج.
6. نسأل سؤالاً غير موجود؛ يمتنع النظام عن اختراع إجابة.

## قائمة فحص عند وصول الملفات

- هل الملفات أدلة عامة أم سجلات أفراد؟
- هل توجد نماذج معبأة أو صور هويات أو كشوفات مالية؟
- هل أسماء الملفات نفسها تكشف بيانات شخصية؟
- هل النسخ ممسوحة ضوئياً وتحتاج OCR محلياً؟
- هل تقرير الاستخراج يعرض `restricted` أو `privacy_review`؟
- هل يمكن حذف بيانات شخصية غير لازمة مع إبقاء معنى الدليل؟
- هل تظهر الصفحة والمصدر الصحيحان في Top 3؟
- هل نجحت مجموعة أسئلة عربية وإنجليزية، وأسئلة يجب أن يمتنع عنها النظام؟
